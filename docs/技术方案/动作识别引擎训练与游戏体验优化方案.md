# BadmintonRally 动作识别引擎训练与游戏体验优化方案

2026-11-22 · 面向 iPhone 游戏、Mac 采集工具、标注与试玩人员。以下录制配额、实验参数和发布门槛均为第一轮建议值；实测基线后在验证集上定稿。

## 1. 第一版要让玩家打成哪几拍

玩家站在电视前，轻挡能回球，连挥两拍能出两次动作，扣杀后自然收手只出一次动作。即使玩家打早、打晚或离球太远，游戏也应能解释这一次挥拍。先做好这三个体验，再扩大可自由选择的专业打法。

| 玩家任务 | 要查的环节 | 验收证据 |
|---|---|---|
| 胸前轻挡一次 | 静止噪声、低幅触发、游戏触球窗 | 录像中的每一拍对应一次检测，另记该球是否成功回击 |
| 快慢交替连抽两拍 | 随挥恢复、第二拍触发、游戏锁定 | 同时显示两次人工事件、检测事件和游戏接收结果 |
| 扣杀后自然收手 | 收手产生的反向峰、重复出球 | 收手即使有大峰也只生成一个有效挥拍 |
| 同一来球主动选吊球或扣杀 | 分类与战术选择 | 同一玩家交替打两种球，统计各自命中和误判 |
| 握姿改变后继续打 | 校准负担、方向漂移 | 记录重校次数、用时和首次成功回球时间 |

## 2. 起点与第一轮产出

逐场检查 57 个 manifest。全部为 P01、右手、机型 iPhone18,1；慢速演示 28 场、正常实战 29 场。56 场 complete、1 场 partial；14 种采集提示，各场 trials_index.csv 合计 0 条人工标注。已有报告估算 IMU 约 100 Hz。现阶段可以分析单人的具体失败、验证导出和回放；跨玩家表现需要独立人群验证。[本机采集检查报告](</Users/hua/Documents/project/BadmintonRally/data/动作采集/动作采集数据检查报告.md>)

游戏的个人校准依次采上挑、下挥、平抽各两次，再验证各一次。识别器要求回到接近初始握姿且低运动持续 120 ms 才重新准备；候选至少持续 45 ms，随后按峰值回落或 320 ms 上限结算。回合层另有 220 ms 锁定、最多 340 ms 识别回溯和站位判定。一次漏球可能发生在这两层中的任意一层。旧训练脚本读取人工接受的五特征 CSV，只覆盖三种基础动作和背景。[SwingCoach](../../code/Clients/iOS/Motion/SwingCoach.swift) · [Rally](../../code/Clients/iOS/Game/Rally.swift) · [现有训练脚本](../../code/Tools/train_strokes.py)

第一轮产出四件东西：一份逐拍复核索引、一组含负样本的连续场次、一份现版逐拍回放结果、一份新旧对照表。下面所写的共享回放、训练导出和发布指标均为待实现方案。

## 3. 录制计划与现场操作

**今天用现有数据开工。** 先复核所有网前放网、接杀挡网、平抽和正手扣杀，再扩到其余类别。用 AEDB484C 的正常放网（主峰 2.96 rad/s）和 BA66D27A 的慢速上挑（23.04 rad/s）检查弱动作与强收手。提示档位记录表演意图，实际强度另算。partial 场次单独检查可用区间和时钟覆盖。

**下一次录制照下表执行。** 先用 P01 试跑一次脚本，确认录制员能区分每个任务。随后建议招募 12 名新玩家，覆盖初学和熟练者、左右手，尽量含至少 3 名惯用左手者和两种机型。每人分两天录制，第二天重新连接和校准。给玩家固定匿名 ID，跨天沿用。人数属于试点预算，少数人群单列人数及结果。

| 每人每天的任务 | 建议数量 | 操作和用途 |
|---|---:|---|
| 静止与握姿校准 | 每次动作任务前保存一组 | 摄像头拍到持机手、肩和随挥范围。连续回合整段视为一个任务；逐拍插入校准会破坏自然节奏 |
| 基础单拍 | 6 类 × 5 拍 | 上挑、平抽、扣杀、挡网、推球、短发。每类 1 拍慢速演示、4 拍正常实战；打乱类别和等待时间 |
| 易混动作 | 任选两对，每对各动作 4 拍 | 同一来球交替做挡网／反抽、吊球／扣杀、反手短发／偷后场。跨人轮换，补齐 14 类；记录实际动作和意图 |
| 单拍收手与真双拍 | 3 组，各 5 次 | 平抽后收手、正反手连续平抽、扣杀后接挡网。保持整段流；自然打出紧凑、中等、宽松间隔，按实测间隔分组 |
| 背景活动 | 2 分钟 | 等球、挪步、换握姿、操作界面、拿起或放下手机。分别标出活动区间；保留误触前后文 |
| 真实投屏回合 | 2 局，每局约 2 分钟 | 一局固定喂球便于版本比较，一局自由对打。记录投屏方式、游戏日志、玩家认为漏掉或多出的拍；抽样同框拍手和电视 |

录前检查画面、磁盘、手机采样和时钟锚点；选手别、提示动作和两档速度之一。录后先确认视频可播、首尾时间可映射、回合日志已落盘，再结束该玩家场次。第二天部分人沿用设备，部分人更换机型，记录变化。镜头遮挡、拿错手、失误都保留原因，避免数据只剩漂亮示范。视频按参与者同意范围本地保存，训练导出默认只带匿名 ID、IMU 和标签。

## 4. 数据模型、标注与导出

保留每个 UUID 目录的原始包。训练集从带版本的索引派生，一拍一行；背景按时间段保存。统一以手机单调时钟秒数为主轴，保留原始视频秒数、帧 PTS 和映射版本，以便重新核对。

| 实体与主键 | 来自当前采集包 | 建议补充或派生的字段 |
|---|---|---|
| 场次 session_id | manifest 的 participant、hand、grip、device、build、prompt、speed、state | 录制日、熟练度、投屏方式、固定喂球方案、数据版本 |
| 样本 (session_id, seq) | samples.csv 的 t_phone、rx/ry/rz（rad/s）、ax_g/ay_g/az_g（用户加速度，g）、gx/gy/gz（重力）、qx/qy/qz/qw | 时间间隔、缺样标记、相对准备姿态；原始列留存 |
| 校准 (session_id, step) | calibration.jsonl、position_targets.json 的目标、时间、重力、四元数及可用的相机证据 | 校准批次、稳定区间噪声、重校原因、质量等级 |
| 时间与视频 (session_id, frame) | clocks.jsonl、frames.csv、camera.mov | 手机到 Mac 的拟合参数、锚点残差、局部帧间隙、可信范围 |
| 标注 (session_id, trial_id) | trials_index.csv 已有 prompt、actual_label、序号区间、视频区间等；action_window.json 给出操作窗口 | 基础挥法、主挥起止、估计击球区间、随挥结束、背景类型、可见性、复核状态、人员与版本 |
| 运行事件 (session_id, event_id) | 建议新增游戏诊断导出 | 候选开始、拒绝原因、估计击球时刻、输出时刻、类别分数、模型版本、来球 ID、位置、游戏接受或拒绝原因 |

**标一拍的操作。** 标注员先看整段，再跳到自动候选峰；补漏掉的小动作，拆开双拍，分别标主挥和收手。空挥的估计击球区间由可见前送或下压阶段确定，记录不确定度。遮挡时可以确认“有挥拍”，类别或时刻留空；对应记录只参加可确认的任务。未复核区间保持 unknown。对 20% 场次及全部争议样本安排第二人独立标注，记录类别一致率与时间边界偏差，争议样本仲裁后入库。

**质量与导出。** 每场检查序号与时间单调、长间隙、非有限数、四元数模长、动作段的校准和视频覆盖。按帧 PTS 对齐，避免用平均帧率换算；时钟拟合残差与摄像头曝光误差分别记录。断流处切段，恢复后重新预热。导出清单含原始包标识、版本、排除原因、玩家分组、类别和背景时长。旧脚本需要适配器从已复核的区间按原定义重算五个特征，生成 participant、label 和五个数值列的 *.accepted.csv；背景行取实际触发过的反例。扩展类别使用独立版本的标签表和导出格式。

## 5. 引擎与训练实验顺序

**实时输入 → 因果滤波 → 候选检测与恢复 → 基础挥法分类 → 回合规则 → 画面与触觉反馈。** Mac 用同一份 Swift 核心按 t_phone 顺序喂入数据，支持逐帧暂停查看状态。现版基线需要玩家三类模板及验证状态；四步空间校准与这组模板用途不同。新场次保存校准配置快照。旧场次用独立的 P01 校准拍建立模板并记录来源；与构建模板重叠的拍从评分中移除，缺少配置的回放注明“重建基线”。

| 实验 | 实现与训练方法 | 升级依据 |
|---|---|---|
| A 现版模板 | 冻结代码、模式、校准与阈值。整场回放记录候选、分类、拒绝时间及原因 | 建立逐拍失败清单，区分检测、分类、游戏判定 |
| B 检测器改动 | 依次对比原信号与单向低通滤波，静止噪声估计触发下限；用较低退出阈值稳定分段。恢复阶段比较“静止回位”与“能量先降、又出现方向一致的新加速”。每次只改变一个条件 | 轻挡和第二拍检出提升，背景误触与收手重复仍达标。统计滤波增加的等待时间 |
| C 小数据分类 | 固定检测器，先比最近质心、逻辑回归或线性 SVM。输入允许在出球时刻获得的峰值、持续时间、主轴、累计转动、上升时间和制动特征。按训练玩家拟合尺度与类权重 | 在相同候选和整场串联两种评估中报告增益；低置信度可拒识，阈值在验证玩家上确定 |
| D 时序模型 | 多玩家、多场景补齐且 C 仍有稳定混淆时，试小型因果 1D CNN 或 Create ML 活动分类器。输入近过去的一段六轴序列，例如比较 160/240/320 ms 历史窗，以 20 ms 步长试验；保留上下文缓存 | 较 C 在未见玩家和低配目标机上有可重复收益，并满足延迟和功耗预算，再导出 Core ML |

校准时记录重力和准备姿态；以相对旋转比较动作方向，使用已知方向的校准动作验证轴序、符号及左右手映射。速度档只作分层评估。标准化参数、数据增强和负样本挖掘仅在训练分组内进行。可尝试实测范围内的小角度握姿扰动；镜像前先用真实左手样本验证旋转轴符号。禁止把摄像头关键点、任务提示、未来的峰值、某一类独有的录制顺序混入手机分类输入。视频用于标注，单手机提供握持端运动证据，全身角色动作由动画驱动。

**划分与复现。** 试点 12 名新玩家可预登记为 8 名训练、2 名验证、2 名封存测试，P01 用于开发诊断。按人分组后再切窗，跨天、相邻拍、重叠窗继承同一组。尽量让训练和封存组都有左手样本。封存两人只能做小规模验收，应列出逐人成绩。记录数据清单、随机种子、代码提交、特征顺序、单位、采样率、超参数和模型文件校验值。用人工真值窗口评估“分对了吗”，另用整场自动流水线评估“玩家这一拍最终得到了什么”。

## 6. 分类结果怎样改善对局

| 观测到的挥法 | 回合允许的结果 | 判定细节 |
|---|---|---|
| 横向快挥 | 平抽、接杀反抽 | 结合来球是否为杀球及回击时机；同一种横挥在普通来球仍能平抽 |
| 向前下方点压、较大幅下挥 | 网前扑球、后场扣杀 | 查询虚拟角色与球在估计击球时刻的位置；保留低球时的容错规则 |
| 短促向前送 | 挡网、网前推球、放网 | 先分接杀和主动网前；同一位置可选多种球时保留预选，并对照玩家选择记录训练对 |
| 由下向上或头顶挥动 | 上挑、头顶高远、吊球 | 用准备方向和前送特征区分；同一高球交替打高远、吊球、扣杀，验证选择权 |
| 发球阶段的挥动 | 正手高远发球、正手短发、反手短发、反手偷后场 | 先用发球阶段限定可选动作。反手短发与偷后场共享准备姿势，需采集末段加速差异；分不稳时支持预选打法 |

建议把“检测到挥动”的角色准备动画与“游戏接受击球”的触觉、出球动画分别触发。只在球权和触球窗成立时改变球路；每个 event_id 最多提交一次。置信度不足、挥早、离球远分别记原因。新旧识别器并行比较时只允许当前启用的引擎控制角色。

## 7. 验收、试放与回滚

评估前冻结标注和匹配规则。以人工估计击球区间为准，初始可向两端各宽容 60 ms，并同时报告更严容差的结果。让预测与人工事件在时间允许范围内一对一匹配，优先最多匹配、随后最小时间差；匹配后再判断类别。单拍附近多出的事件计重复，背景活动中的事件按分钟计误触。无可靠时刻标注的拍只参与可判定的指标。

| 指标 | 试点建议门槛 | 采集和报告方式 |
|---|---|---|
| 轻挡、短发的逐拍检出率 | 各 ≥90% | 按动作、手别、玩家、速度列出分子和分母；同时列分类正确率 |
| 连续第二拍检出率 | 正常实战 ≥90% | 按实测拍间隔分桶；另列两拍均正确且无多余事件的比例 |
| 收手重复与背景误触 | 重复 ≤2 次/100 个单拍；背景 ≤0.5 次/分钟 | 同时报背景总分钟、误触动作和最差玩家 |
| 手机反馈等待 | 输出时刻减估计击球时刻，P95 暂定 ≤100 ms | 同时报中位数、负偏差及视频标注误差；分别在正常和低幅动作上计算 |
| 投屏手感 | 同设备、同投屏路径，新版电视端 P95 不劣于旧版 | 外部录像同框拍手和电视，以帧为单位计时，记录帧率。固定喂球比较成功回球率、有效连续回合数、首次成功用时及主观延迟感 |

对照试玩以玩家为单位交叉新旧顺序，相同来球脚本、相同投屏链路；另做自由对局复查。给出逐人差值与样本数；少数玩家或少量轻挡造成的大幅波动标为待补样。新模型先在开发版旁路记结果，再小范围切换。保留模板引擎和旧参数，可按版本回退。离线和真机用同一输入比对事件时间及类别；发生异常、模型加载失败或性能退化时回退至已验证的引擎。

## 8. 开发交付顺序

1. **Mac 复核与回放。** 历史页并排显示视频、六轴曲线和引擎状态；能补标漏拍、拆双拍、标背景。交付一段单拍和一段双拍的逐事件回放，重复运行结果一致。
2. **建立基线并按失败补录。** 完成 P01 复核，按第 3 节试录，再扩到新玩家。每周按“漏检、重复、错类、时机、距离”排序，优先补最常见失败及外观相近的成功对照。
3. **先改检测，再训分类。** 先对比第二拍恢复规则，再固定检测器比较分类模型。每次实验附数据版本、失败片段、端侧延迟和保留或撤销结论。
4. **接入游戏并验收。** 先验证平抽／接杀反抽，再验证扑球／扣杀。记录接受、拒绝和投屏反馈；达到第 7 节预先定稿的门槛后扩大试用。将新发现的失败纳入下一版开发集，同时另建独立验收集。

## 9. 可借鉴的公开实践

- 任天堂在 Wii Sports Resort 开发访谈中描述了连续挥动后出现偏差、再用明确的单挥任务验证控制的过程。本项目可借鉴其可重复的玩家任务，商业游戏的内部判定阈值仍未知。[任天堂开发者访谈](https://iwataasks.nintendo.com/interviews/wii/wiisportsresort/0/2/)
- BadminSense 从连续运动记录中定位候选、切分和分类。可借鉴分阶段评估；手表位置与手握手机不同，需要重新采集和验证。[BadminSense 论文](https://taizhouchen.github.io/docs/badminsense.pdf)
- 开源球拍 IMU 研究提供分段、特征模型、CNN 和空挥样本。其居中 1 秒窗口会用到动作中心之后的观测，适合离线对照。开发实时模型时记录首次可输出的时刻，并统一加速度与角速度单位。[开源羽毛球识别项目](https://github.com/PhusNguyen/Realtime-IMU-Badminton-Stroke-Recognition)
- Apple 的 MLActivityClassifier 支持运动传感器时序分类与 Core ML 模型导出，可用于模型 D 的平台对照。连续拍切分、游戏事件去重和玩法映射仍由项目实现。[Apple 开发文档](https://developer.apple.com/documentation/createml/mlactivityclassifier)

## 10. 第一轮落地工单

**本轮交付目标**：开发者在 Mac 打开一个真实场次，能指出“第二拍发生在这里，引擎在等待回位，所以没有出事件”，或“引擎出了事件，但回合仍处于锁定”。同一个场次可以重跑旧版与候选版，逐拍查看差异。下面按依赖顺序实施。日程按一名开发者的试点安排估算，招募与真实投屏试玩另计。

### 第一个版本如何作决定

1. 用单独录制的个人校准数据初始化旧版与候选版，两版共用相同输入和模板。没有个人模板时只展示信号与人工真值，或明确标记重建校准的结果。
2. 同屏列出五个原始计数：C 检出几拍、B 与 D 的第二拍各检出几次、A 多出几拍、E 误触几次。每次变化能点回对应录像。D 的第二拍即使被分为错误球种，也分别记录“已检出”和“分类错误”。
3. 如果候选根本没启动，先检查触发或恢复；如果已经输出 hit，再查游戏锁定与触球时窗。若两版在 C 都漏检，则另开轻动作检测实验。若 A 的收手误触增加，回到逐拍回放修恢复规则。
4. P01 试玩通过才投入多人试验。第 7 节的门槛用于后续独立玩家验收；首轮 5 次双拍只用于定位失败。工具交付、单人改善、多人可发布分别记录结论。

## 11. 已落地的动作曲线训练与客户端接入

### 第一批训练结果（2026-11-22）

曲线版本 a37dd4670d3190a9。训练器从 Mac 场次读取 IMU，检查完整性、序号、时间与有限数，按场次操作窗口和时钟映射定位角速度主峰。56 个完整场次各提取一条弱标签曲线，另一个 partial 场次已列入排除清单。14 类各 4 条，每类按场次 UUID 排序留出 1 条，共 42 条训练、14 条留出。首版训练与留出均为 P01。同一训练器也可以读取人工复核的多拍索引，逐行提取可对齐的片段；一旦有人工标注，就以人工索引为准。

每条曲线的 16 个采样点覆盖已观察到的峰前 150 ms 至峰值，按手机时间线性插值。每个点保留机身三轴角速度及三轴用户加速度，两个传感器分别按整窗 L2 范数归一化，再计算同类均值原型并归一化。端侧用余弦相似度匹配，单拍只计算一次。原始力度仍以峰值、原始六轴和采集包保留。开源球拍研究的分段及六轴特征给出参考，本版选择仅使用峰及其过去的波形，便于在比赛候选结束时立即匹配。[训练器](../../code/Tools/train_curves.py) · [Swift 推理实现](../../code/Clients/iOS/Motion/SwingCurveModel.swift) · [参考项目](https://github.com/PhusNguyen/Realtime-IMU-Badminton-Stroke-Recognition)

留出集与采集提示相符 **3/14**，分别为反手短发、反手偷后场和网前扑球各一条。每类只留出一次，场次提示也可能与实际动作不同。此项实验只衡量已选主峰的分类；漏检、重复和实战延迟仍需连续回合与独立玩家测试。初版导出的 Swift 曲线与 Python 在全部 56 条真实样本上逐分量对齐（容差 1e-7）。

### 复训、发布与回退

在项目根目录运行，Python 环境需有 NumPy。每个输出目录使用新版本名。首版允许从单拍任务提示引导提取；以后默认只读取已复核标签。每次扫描按场次逐个处理，有数百至数千条样本时仍只向 App 分发每类一条原型，原始训练数据留在开发机。

```sh
python3 Tools/train_curves.py "$HOME/Documents/project/BadmintonRally/data/动作采集" "$HOME/Documents/project/BadmintonRally/data/挥拍训练/初版复现" --allow-prompt

python3 Tools/train_curves.py "$HOME/Documents/project/BadmintonRally/data/动作采集" "$HOME/Documents/project/BadmintonRally/data/挥拍训练/多人-v2" --holdout P09 P10
```

每版生成 curves.jsonl（含逐拍曲线、来源与分组）、review.csv、report.json、SwingCurves.json。导出包和原始包同一场次应只选一个副本；重复编号会终止训练。保留冻结的发布测试组，模型调参另用训练人员中的验证组。定期增加一批新玩家做盲测，减少反复查看同一留出集带来的偏差。

更新客户端时先检查 report.json 的每类混淆、标签来源与留出人员，再对比整场漏拍和误触。验收后用该版 SwingCurves.json 替换 Clients/iOS/Resources/SwingCurves.json 并重新构建应用；回退时换回上一个版本包的同名文件。升级和回退均可在「设置 → 动作曲线实验」核对版本。该资源随 App 构建发布。

首版正常游玩时计算并显示最近一次候选的曲线匹配结果，默认旁路观察。打开实验辅助、重新完成个人校准后，只有在该类校准验收拍中强匹配、且实时曲线与个人模板第一名一致时，曲线才可帮助通过一个方向接近的候选。初始试验条件为余弦 ≥0.80、曲线前两名差 ≥0.08；个人方向 ≥0.70，个人前两名差可从 0.08 降至 0.03。限定上挑、下挥、平抽三个游戏输入。其他专业动作保留用于观察与训练。模型缺失或格式不兼容时使用个人模板。该辅助位于挥拍候选检测之后，恢复策略与连续第二拍检出仍是独立实验。

当每类累积到数百条，按第 5 节在相同人群划分上比较多原型、线性分类器和因果时序模型。重点复查同动作不同握法是否形成多个明显簇，再决定是否升级单原型结构。改变输入窗、通道、归一化或原型结构时升级 schema，同步训练器与 Swift 推理并重跑回放验证。
